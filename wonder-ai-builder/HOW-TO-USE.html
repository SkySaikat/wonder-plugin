Wonder AI Builder

Bulk-generate WordPress pages and posts from a spreadsheet. Replaces Wonder Page and Wonder Blog with one plugin, at roughly 3–6% of their running cost.

What it does

You upload a spreadsheet. Each row becomes a page or a post: written by an AI model, given a featured image, given JSON-LD schema, and saved as a draft. Generation happens on the server — once queued, you can close the tab, shut the laptop, and go home.

The three things that make it cheap

1. Images come from the media library you already have, matched in PHP. Free. 2. Schema is built in PHP, never asked of the model. Free. 3. The shared brief is sent once per import as a cached prefix, not once per row.

1. Install

1

Deactivate the old plugins

Deactivate Wonder Page and Wonder Blog. Do not delete them yet — leaving them in place keeps their data intact as a rollback path. This plugin never reads or writes their tables.

2

Upload and activate

Copy the wonder-ai-builder folder to wp-content/plugins/, then activate it. Activation creates six tables and schedules the queue worker.

3

Check for a red notice

If any table failed to create you will see an error at the top of wp-admin naming it. Do not proceed — fix database permissions first, or every row will silently vanish on import.

2. Server cron important

WordPress’s built-in cron only fires when somebody visits the site. On a quiet site, a queue of 100 pages will barely move. Set up a real cron entry so generation runs unattended.

Recommended — WP-CLI, which bypasses the web server entirely (no PHP-FPM timeout, its own memory limit, works with zero traffic):

* * * * * cd /path/to/site && wp wab run --quiet >/dev/null 2>&1

No WP-CLI? Hit wp-cron.php instead:

* * * * * curl -fsS -m 55 "https://example.com/wp-cron.php?doing_wp_cron" >/dev/null 2>&1

Then disable the visitor-triggered version in wp-config.php:

define( 'DISABLE_WP_CRON', true );
Every minute is fine

The worker throttles itself to one run every 20 seconds, skips entirely when nothing is queued (one indexed query, ~30ms), and refuses to start when server load is high. A frequent trigger just means less waiting before a queued job begins.

The dashboard shows the exact commands for your install, with real paths, and warns you if ticks stop arriving.

3. API keys

Two ways. For one site, paste them into Wonder AI → Settings. For many sites, use constants — the keys then never touch the database, backups, or staging clones:

define( 'WAB_FAL_API_KEY',       '...' );  // images
define( 'WAB_GEMINI_API_KEY',    '...' );  // text + images
define( 'WAB_OPENAI_API_KEY',    '...' );  // text
define( 'WAB_ANTHROPIC_API_KEY', '...' );  // text

Constants win over anything saved in the admin, and the field is disabled with “Set in wp-config.php” so nobody is confused about which is live.

Keys are never sent to your browser

Settings shows a mask like sk-a••••f2c9. Leaving a key field blank keeps the stored value. This is deliberate: the previous version printed the full key into the page HTML, where any script on the page could read it.

The Schema column

Paste your JSON-LD straight in — the whole thing, <script> wrapper and all if that is how you have it. It is validated, then written into the page after creation. The model is never shown it and never asked about it, so it costs nothing.

Five placeholders get filled in after the page exists, which is information no model could have known:

PlaceholderBecomes
{{url}}The final permalink
{{title}}The generated title
{{image}}Featured image URL
{{date}}Publish date, ISO-8601
{{site}}Site name
 
{"@context":"https://schema.org","@type":"Service",
 "name":"{{title}}","url":"{{url}}","image":"{{image}}",
 "provider":{"@type":"LocalBusiness","name":"Shoot Bright","telephone":"+97140000000"},
 "areaServed":{"@type":"Place","name":"Dubai Marina"}}

Leave the column out and schema is built automatically from the row — LocalBusiness, Service, Article, BlogPosting, Product, or FAQPage, plus a BreadcrumbList. Also free. If your JSON is malformed, it logs a warning and falls back to the auto-built version rather than shipping broken markup to Google.

Running a batch

1

Pick Pages or Posts

The switch at the top. It changes schema type, category handling, and templates.

2

Choose depth, images, speed

Defaults are sensible. See the sections below.

3

Upload the file

Row count appears immediately, with a mapping grid.

4

Check the mapping

Auto-detected values are pre-selected. Correct anything wrong; set unwanted columns to “skip”. Import rows saves them — nothing is generated and nothing is spent yet.

5

Test image matching

Runs the matcher against the first five rows and shows the actual pictures it would pick, with a hit-rate percentage. Free, and it corrects the cost estimate using your real library coverage.

6

Queue generation

Shows the total estimate and refuses to start if it would exceed today’s budget. Then you can close the tab.

Closing the tab is safe

The queue lives on the server. The dashboard only reads progress — it never drives it. Polling pauses when the tab is hidden and resumes when you come back.

Economy submits all the writing as one asynchronous batch at half price. Images and publishing still happen locally, so only the text is deferred. Needs at least 10 rows — below that it quietly uses Standard, because the wait is not worth it.

Choosing Economy with Anthropic is not an error — it tells you plainly and runs at Standard price.

Nothing gets stranded

If a batch fails, is cancelled, or goes quiet for 48 hours, its rows return to the normal queue and generate at full price. Slower and dearer beats losing the work. And once the text has been paid for, a later failure never re-bills it.

How images are chosen

Featured image, cheapest first: 1. Already resolved for this row? --> reuse $0.000 2. Match in your media library? --> use it $0.000 3. Generate (if enabled) --> fal / Gemini $0.003+ In-content images: ALWAYS the library. Never generated. Never billed.

Matching is pure PHP — weighted keyword overlap across alt text, title, caption, description, filename, and the categories of whatever post the image is attached to. Landscape crops score higher because most themes handle them better. No API call, so it costs nothing and adds no latency.

Among equally good matches it picks the least previously used one, so a 100-page import spreads across your library instead of stamping one photo onto every page. In-content images are matched against each section’s own H2, so the picture suits the section it sits in.

Usually better, not just cheaper

Sites with a few hundred published pages already own real, on-brand, CDN-cached photography. That generally beats a generic AI render — and it is free.

Setting the length

Four places can decide how long a page is. The most specific one wins:

#WhereScope
1A Words column in the spreadsheetThat one row
2Import screen → Exact word countEvery row in that sheet
3Settings → Default word countEvery sheet on the site
4The depth preset aboveFallback when all three are blank or 0

Anything from 120 to 4,000 words is accepted and applies to pages and posts alike, in both Standard and Economy mode. The number you type is a floor, not a ceiling: the prompt states an explicit minimum and a per-section word budget, because a model given an approximate target treats it as an upper bound and stops early — asking for “~450 words” measurably produced 303. Expect to land on or slightly above the figure you ask for.

Why Standard, and it is an SEO argument rather than a cost one. Google’s helpful-content systems penalise near-duplicate doorway pages. Short is templated enough to look like one at scale. Long costs roughly twice as much for quality gains that do not move rankings on low-competition location terms. Standard keeps the genuinely local content unique and shares only the boilerplate that was never going to rank.

Every depth except Short also rotates page structure across a location set — a different opening angle per row, distributed evenly — so 100 pages do not fingerprint as a farm. That rotation is computed in PHP, free.

Set a daily budget

Enter a figure in Settings and the queue stops itself when it is reached, rather than discovering the overshoot on your invoice. The 100-row estimate is also checked before queueing.

Command line

wp wab status              # queue, spend, and health
wp wab run                 # process one batch now
wp wab run --force         # ignore throttle and load guards
wp wab run --max-jobs=10   # override jobs per batch
wp wab pause               # stop taking new work
wp wab resume

wp wab status is the fastest way to confirm a site is healthy, and the right thing to loop over when checking a fleet.

Troubleshooting

Nothing happens after queueing

Almost always cron. Run wp wab status — if “last tick” says never or is many minutes old, the cron entry is missing or failing. See Server cron. The dashboard warns about this on its own.

“Daily AI budget reached”

Working as designed. Raise the budget in Settings, or wait for the date to roll over.

Every image is the same photo

Your library has few matching images, so the same one keeps winning. Use Test image matching to see the hit rate. Improving alt text on your existing images is the cheapest fix; switching to “Library first, then generate” is the fastest.

Jobs failing with “content too short”

The model returned too little to publish. Usually a thin row — add a Description brief. This is deliberately not retried, because a retry would bill again for the same outcome.

Server feels slow during a run

Lower Pages per minute, or set Pause above server load to a lower number. The worker already skips ticks when load is high; this makes it more cautious.

A batch has been pending for hours

Normal — the target is 24 hours and it is usually much faster. Nothing is lost: after 48 hours the rows return to the normal queue automatically.

200-site deployment

  1. Put all four WAB_*_API_KEY constants in each site’s wp-config.php via your provisioning tool.
  2. Configure one site fully, then Export config and Import config on the rest. Keys are never included in the export.
  3. Add the WP-CLI cron line per site. Each install computes its own 0–59s offset from its URL, so 200 sites do not all wake at :00.
  4. Verify with a fleet loop: for d in /sites/*; do (cd $d && wp wab status); done
Limit how many sites generate at once

Each site caps itself at one worker using about 80 MB. Idle sites cost almost nothing. But 200 sites generating simultaneously is roughly 16 GB of RAM.

Run bulk generation on 10–20 sites at a time. At ~33 minutes per 100 pages, 20 sites in parallel still clears 2,000 pages in about half an hour, peaking near 1.6 GB. The load guard will start skipping ticks if you overshoot, but treat that as a safety net, not a plan.

Safety & limits

Throughput

About 180 pages/hour per site — roughly 3 per minute. Around 94% of that is waiting on the model, not the plugin. Raising “Pages per minute” above 3 will not help; the 45-second-per-tick guard is the real limit, and it exists to leave the server a quarter of every minute free.

Resources per site

Concurrent workersExactly one, enforced by a database lock
Peak memory~80 MB
Database load~49 queries/job, ~2.5 queries/second sustained
Idle costOne indexed query, ~30ms
Disk~80–200 KB per generated image; zero for library reuse

Permissions

  • Editors can import spreadsheets, queue generation, and manage the queue.
  • Administrators additionally control settings, API keys, budget, and cancelling all queued work.

Review before publishing

Pages are created as drafts by default. Keep it that way. AI copy needs a human pass — for factual claims especially. The model is instructed never to invent prices, awards, certifications, review counts, or years in business, but instructions are not guarantees.

Before a first production run

Install on one staging site. Set the budget to $1. Import 5 rows with “Existing library only”. Confirm wp wab status shows ticks arriving and read the five drafts end to end. Only then scale up. Do not go to 200 sites until 5 rows are clean.
